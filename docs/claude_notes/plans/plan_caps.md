# Plan: capabilities (`caps`) in the playground

## Context

The author's other OCaml projects (osemgrep, efuns, mmm, xix) pass
their authority explicitly: a function that writes a file takes a
`Cap.open_out`, one that exits takes a `Cap.exit`, and all of them come
from one `Cap.main` at the program's entry. The library is now its own
opam package, **`caps` 0.1.0** (aryx/ocaml-caps, installed in the
switch 2026-09-21), so this repository can use it the same way. The
occasion is [`plan_io.md`](plan_io.md) -- the apps saving documents --
but the subject is wider: **what in this repository touches the world,
and should say so in its types**.

This plan is only about capabilities: the dependency, where
`Cap.main` goes, which existing code needs which capability, and the
Semgrep rules that keep the rest honest. What the apps save and how is
`plan_io.md`'s.

## What caps is, in two lines

Abstract types that cannot be forged (`Cap.open_in`, `Cap.open_out`,
`Cap.exit`, `Cap.network`, `Cap.random`, ...), obtained only through
`Cap.main : (all_caps -> 'a) -> 'a`, called once; a function's
signature then lists the authority it needs, narrowed with `:>`, and
wrappers (`CapStdlib`, `CapSys`, `CapUnix`, `CapRandom`) are the
capability-aware versions of the dangerous Stdlib functions. The
Semgrep rules in `ocaml-caps/rules/` (`forbid_fs`, `forbid_exit`,
`forbid_console`, `forbid_network`, `forbid_misc` -- random and
`Obj.magic` --, ...) forbid calling the unguarded ones.

## What touches the world today (inventory, 2026-09-21)

Non-test code only; the tests and `scripts/` are programs of their own
and can take `Cap.main` in their mains later.

- **The native loops** (`playground/native_common/Native_loop_2d.ml`,
  `Native_loop_3d.ml`): `Sys.argv` (the
  `-script`, `-dump-frame`, ... flags), `exit` (on Q, on the window's
  close, after `-dump-frame`), `open_out_bin` (writing the dumped
  frame), `Unix.gettimeofday` and `Unix.sleepf` (the frame clock).
- **Images** (`graphics/images/Download.ml`, `Image_decode.ml`):
  `Curl` (downloading an image URL) and `open_in_bin`/`open_out_bin`
  (the file, and its downloaded copy) -- network and file system.
- **Warnings** (`playground/Audio.ml`, `playground/native/
  Playground_platform.ml`): `prerr_endline`.
- **Randomness** (`Tetris.ml`, `Snake.ml`):
  `Random.self_init` -- the one place the games are not deterministic,
  and exactly what `Cap.random` is for.
- **Time** in a game (`Tetris.ml`: `Unix.gettimeofday`), and
  `core/Basics.ml`'s `Printf.printf` (Elm's `Debug.log`).

## The design

- **`Cap.main` is called by the program, not the playground.** An app
  that saves writes
  `let main = Cap.main (fun caps -> Playground_platform.run_app (app (caps :> < Cap.open_in; Cap.open_out >)))`,
  and its `update` closes over the narrowed object. A game or an
  example that needs nothing keeps
  `let main = Playground_platform.run_app app` -- and that absence *is*
  the information: it cannot touch a file.
- **The platform is the trusted computing base.** The backends'
  `Playground_platform.ml` and the native loops talk to SDL, the
  browser, the clock; they are the `caps.tcb` side, excluded from the
  rules, and say so in their headers. What they *offer* to programs
  takes capabilities (`plan_io.md`'s `store`, `fetch`, `export`).
- **The user's gesture is a grant.** A file dropped on the window, or
  chosen in a file dialog, is read by the platform and handed to the
  program without any capability on the program's side: the
  **powerbox** idea of capability-based UIs (the system, not the
  application, opens the file the person chose). `plan_io.md` uses it
  for Import; it deserves its paragraph in the `.mli`.
- **Randomness**: `Random.self_init` in Tetris and Snake becomes
  `CapRandom` with a `Cap.random` from their `main` -- and the other
  games' determinism (the reason the golden frames work) becomes
  visible in their types. Optional, and a good first small change.
- **Warnings** on stderr from inside the playground stay an ambient
  authority, as `caps` itself treats logs; the rule excludes them or
  they go through `Logs`.

## The web

`caps` links `unix`. `Cap.main` only builds an object, with no system
call, so it should run under js_of_ocaml once linked; js_of_ocaml's
`unix` stubs may warn about missing primitives at link time. If that
gets in the way: link `caps.tcb` (no dependencies) where possible, or a
small change upstream in `caps` (splitting the Unix wrappers from
`Cap` itself) -- the author's library, so both are open. On the web
the capability types keep their meaning as *authority* ("may write the
document named this"), whatever the storage behind them is.

## Phases

1. `caps` as a dependency in `dune-project` (for the packages that
   need it; `.opam` files regenerated by `make`), and one program using
   it end to end -- the first saving app of `plan_io.md`. **Done**
   (2026-09-22): `elm_playground` depends on `caps` (its
   Playground_platform's `store`, `fetch`, `stored`, `export` take
   `< Cap.open_out; .. >`, `< Cap.open_in; .. >`, `< Cap.readdir; .. >`),
   and the ten saving apps call `Cap.main` in their main, narrowing to
   `File_menu.caps`; the platforms only ask for the capability, never
   hold one.
2. The web: check `caps` links under js_of_ocaml (an `apps/web/` app
   with `Cap.main` in it). **Done**: it links and runs, with no
   missing-primitive warning.
3. `Cap.random` for Tetris and Snake.
4. The Semgrep rules of `ocaml-caps/rules/` added to this repository's
   `semgrep.jsonnet`, with the platform (the TCB) excluded, and `make
   check` clean -- which is where the inventory above either gets its
   capabilities or its explicit exclusion.
5. Optional: the native loops' own authority made explicit (their
   `Sys.argv`, `exit`, frame dump) -- they are the TCB, so this is
   documentation more than security.

## Later: ocaml-commons

`ocaml-commons` (aryx/ocaml-commons) completes `caps`: `FS`
(`with_open_in`, ...), `Console`, `Exit`, `Fpath`, `Proc`, .... Worth
adopting once the above works, so that capability-taking code reads and
writes through `FS` rather than `CapStdlib` directly. To settle first:
it has modules named **`Cmd`** and **`Set_`**, the same names as this
repository's `core/Cmd` and `core/Set_` (all unwrapped libraries), so
linking both would clash -- a rename on one side, or wrapping.
