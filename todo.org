*** switch Playground.image's string src to Uri.t?
right now playground/Playground.mli has
  val image : number -> number -> string -> shape
switching the src param to Uri.t would touch both backends (native
Image_native.ml/curl, web Playground_platform.ml/img src), plus every
example passing an image url (Mario.ml, Turtle.ml, and their _js copies).

checked the dependency cost: uri pulls in stringext and angstrom
(which itself pulls bigstringaf), all pure OCaml / light C stubs, no
new system libraries, so not too heavy on its own. the bigger cost is
the API-surface churn (public Playground.mli + both backends + every
example), not the dependency. skipped for now.

*** rethink Playground.image's loading model (not just its src type)?
val image : number -> number -> string -> shape is a *pure* function --
works well on web because the browser gives async fetch/decode/cache
for free behind <img src>/<svg:image href>. native has nothing like
that built in, so the native backend keeps having to bolt a loading
strategy onto that same pure-looking API: synchronous (blocks/crashes
the frame on a cache miss), background-thread-async (tried it for
Mario's sprites -- works, but needs a Mutex-protected cache + creating
Cairo surfaces off the main thread, and the image still visibly pops in
~1s into gameplay instead of being there from frame 1), or the
preload_image-based prefetch we landed on for Mario (see
Playground_platform.preload_image, examples/Mario.ml's init) -- which
is really just "do what every other game does: load assets in a
loading phase before the game loop starts", not something [image]
itself does for you.

preload_image works but only because Mario happens to know all its
sprite urls upfront; it's not a general solution for an app that
discovers image urls dynamically. worth someday considering an
explicit asset-loading step in the Playground API itself (e.g.
something Cmd/Task-based, matching how Elm's own effect system would
do it) rather than always pushing this back onto each game/example.

*** DONE let each game/example see argv (its own CLI flags), not just -v/-debug/-quiet
claude: done as Playground.flags (name=value arguments natively,
?name=value on the web, in computer.flags); see examples/Flags.ml and
README.md's "Parameters (flags)".
right now playground/native/Playground_platform.ml's run_app/preload_image
parse Sys.argv themselves (-v/-verbose/-debug/-quiet, see
parse_cli_and_setup_logging) and Arg.Bad on anything else, so a game
can't add its own flags (e.g. "-level 5", "-speed fast") without editing
Playground_platform.ml itself.

could pass the remaining/unparsed argv down to the app (e.g. as part of
computer, or an extra arg to game/picture/animation) so each
example/game decides what to do with its own flags on top of the
shared ones. harder on the web backend since there's no real argv in a
browser -- would need to read "?xxx=yyy" query-string params from the
page URL instead (Window.location or similar) as the web equivalent.
