** playground3d (new)
- new elm_playground_3d library (Playground3d.mli), same Model-View-Update
  API as the 2D one: shape3d (cube, box, sphere, textured_quad,
  textured_cube, group3d), camera, lighting, flat/Gouraud/Phong shading,
  a HUD overlay (Playground3d.hud), portable rendering hints
  (Playground3d.rendering: shading, culling, textures), and cached3d
  (like Elm's Html.lazy, lets GPU backends keep a mesh in GPU memory)
- four backends: software (from-scratch rasterizer on SDL), web (reuses
  the 2D SVG renderer with a painter's algorithm), OpenGL (tgls) and
  WebGL, the last two sharing Gpu_scene and graphics/gpu/Mesh_cache;
  TinyMinecraft went from ~6.5s to ~1ms per frame on OpenGL with cached3d
- textures from local files or http(s) urls, preload_texture, a magenta
  placeholder when a texture fails to load
- examples3d/ (Cube3d, Cubes3d, TexturedCube3d, InteractiveCube3d,
  Spheres3d, FloatingCity3d, PaintersAlgorithmFail3d, Corridor3d,
  CachedGrid3d) and games3d/ (StarCollector3d, TinyMinecraft, a port of
  tiny-minecraft), each also built for web/opengl/webgl via copy_files
- fixes: spheres missing their top cap (Newell's method for face
  normals, the pole made the cross product 0 then NaN), 1-pixel cracks
  along shared triangle edges, a GC-timing bug in tgls'
  glShaderSource binding (Gc.full_major before compiling shaders)

** graphics/ (new, from-scratch rendering algorithms for teaching)
- private libraries independent of the Playground, one idea per module
  with its .mli explaining it (ASCII diagrams, paper references):
  core/ (Framebuffer, Blit, Opti), 2d/ (Fill scanline polygons, Line
  Bresenham, Circle midpoint, Stroke, Magnifier, geometry/Vec2), 3d/
  (Project, Cull, Clip, Zbuffer, Interpolate, Shading, Texture,

  Render, geometry/ Vec3, Mat4, Camera, Lighting), font/ (Hershey vector
  fonts), images/ (Image_decode, Texture_decode, Rgba, Download), gpu/
  (Mesh_cache)
- unit tests in graphics/tests/ checking the worked examples of the .mli

** playground (2D)
- new software backend (elm_playground_software): a from-scratch 2D
  rasterizer on SDL (filled polygons, lines, circles, images by inverse
  mapping with bilinear/nearest filtering, Hershey text, antialiasing)

  smooth_images) for run_app, honored by the Cairo, software and web
  backends; Mario uses it for sharp pixel-art sprites
- native_common/ (Native_loop_2d) shared by the Cairo and software
  backends
- fix: stb_image with ~channels:4 truncated RGB images (read past the
  end by Cairo); now load with the file's channels and expand to RGBA

** debugging and testing
- runtime-toggleable debug keys in the software backends (wireframe,
  bounding boxes, transparency, pixel magnifier, z-buffer vs painter,
  backface culling, perspective-correct vs linear, antialiasing,
  filtering, optimizations on/off, mesh cache), "h" for a help panel,
  only enabled with -debug-keys
- "r" in the software backends: a half, a third or a quarter of the
  resolution, each pixel a 2x2 to 4x4 block (graphics/core/Pixelate),
  the look of 320x200 games and about k^2 less per-pixel work
  (TinyDoom3d 125ms -> 15ms a frame at a third); "u" in the OpenGL one:
  the HUD off, to tell if it's what's slow
- native flags -uncapped, -fixed-time t, -keys k, -dump-frame n file
  for deterministic frames; -v/-debug now also work in 3D
- golden frame tests (tests/2d/, tests/3d/) in make test, every software
  example rendered offscreen and compared pixel by pixel;
  make approve-golden2d/3d
- scripts: xdrive.py (drive a running app's mouse/keys via XTEST),
  ref_frames_3d.sh, bench_playground.sh, screenshot_playground3d.sh,
  smoke_test_playground3d.sh

** playground layers (2D, on top of Playground)
- Camera2d (window/lock/lerp following, zoom, clamp, an angle and
  turn_toward), Tilemap (levels typed as strings), Sprite (pixel art
  from strings, animated), Scene2d (title/playing/over scenes, keys
  pressed), Physics (see below), Audio (see below)
- Playground.flags: a program's parameters, name=value natively,
  ?name=value on the web (Playground_platform.flags); a seed=n flag
  for the games' randomness
- relative mouse motion (mdx/mdy), run_app3d ?capture_mouse (FPS look)
- Puzzlescript (new): a game as things on layers, a map and a few
  rewrite rules, after PuzzleScript (Stephen Lavelle, 2013) -- the
  third way of programming borrowed into playground/, beside Logo's
  turtle and Bigbang's world programs, and the one that takes the game
  over: no update function and no view, only data. The whole of
  Sokoban is
    rule "> @ | $  ->  > @ | > $"   and   win = all_on '$' '.'
  Things live on layers, which is what keeps a crate on a target from
  being a thing of its own and the rules from doubling; a turn is:
  mark what the player moved, run the rules until the board settles,
  move what is still marked (it goes if its layer has room there),
  then the late rules. examples/PuzzleScriptSokoban.ml (one rule) and
  examples/PuzzleScriptBoulders.ml (four: digging, pushing, gravity,
  taking a diamond) are two games out of that one engine. Its .mli
  carries the lineage: Papert's Logo, KidSim/Stagecast Creator,
  Repenning's AgentSheets, TileCode

- games2.5d/ (new): the pseudo-3D games moved together, with a README
  comparing their tricks and their sizes -- TinyWolfenstein, TinyOutRun,
  TinyKart, TinyDoom, TinyComanche -- and TinyDescent, which is full 3D
  on the 2D playground: its own projection and clipping, the mine
  walked through its portals, cells painted farthest first, no z-buffer;
  each game's trick now marked in its source (grep "the trick of this
  game" games2.5d/*.ml) with how many lines it takes
- games2.5d/TinyDungeonMaster: the oldest and simplest of those tricks,
  and the first one to read -- from a cell's center, looking along an
  axis, every cell in view has one fixed place on the screen, so the
  view is nested frames filled in farthest first: 24 lines, and no
  arithmetic per frame (FTL's artists painted those pictures by hand).
  Around it is what Dungeon Master (1987) actually invented, which was
  not the pixels but the game: real time, and a world you act on -- the
  iron key and its door, the lever and the portcullis, monsters on
  their own clock (a monster that has just moved cannot strike yet:
  the "dance"), a torch burning down, a panel telling you about it all.
  ai/Pathfind's A* walks the monsters; tests/games checks the dungeon
  is winnable in that order, and the dance rule
- games3d/TinyTombRaider: Tomb Raider (1996), in a tomb. The one
  character here with no velocity: a vocabulary of moves, each a fixed
  number of frames over a fixed distance, committed once started, so
  the outcome is settled at take-off and there is no collision
  detection in the file at all. That is what makes the level countable
  -- a running jump is always two squares, so a chasm one square wide
  is a question with an answer -- and tests/games writes the whole
  route down as the level's answer. Textures by the era's technique: one
  texture page (games3d/tomb.png, drawn by
  scripts/build/make_tomb_atlas.py with fractal noise), a sub-rectangle
  per face, one textured square per square of wall, and the page
  crushed into one 16-colour dithered palette. kits/puzzle's Push, from
  TinySokoban, moves the block: the first 3D game on a 2D kit
- games3d/texture.png is now games3d/minecraft.png, beside tomb.png
- games3d/TinyBlockout: BlockOut (1989), Tetris down a well. The rules
  are Tetris with one more index (a layer is full when its cols x rows
  cells are), and a quarter turn is the piece's bounding box turned --
  integers, no trigonometry, four turns the identity. The rest, and
  most of the file, is depth cues, because from straight above you
  cannot tell how deep anything is: cubes darker the deeper they lie,
  and the well's ring lit at the level the piece will land on, since a
  view from straight above cannot have a drop shadow (the shadow is
  always exactly behind the thing casting it)
- physics/3d/ (new, the 3D physics engine's first phases, beside
  physics/2d/ and for the same teaching: one idea per module, each .mli
  with its diagram, worked example and references; see
  plan_physics3d_teaching.md and notes_3d_physics.md). Metres and
  seconds, not pixels. Quat (orientation: why not three angles, the
  half-angle, q' = 1/2 w q), Mat3 (the inertia tensor, and R I R^T),
  Body3d (position, velocity, orientation, spin, the tensor and its
  inverse; the tensors of a box and a sphere and the 3D parallel-axis
  theorem), Integrate3d (the four 2D methods with a z, plus the
  rotational half) and Energy3d (energy, momentum, angular momentum:
  the referee). The step follows L, not w: dL/dt = torque has no
  gyroscopic term, and w read back as I_world^-1 L wobbles anyway
  because the tensor has turned -- measured, |L| drifts 1e-11 that way
  against 2e-2 stepping w with the gyroscopic term. All three laws are
  switchable, because the third one (no gyroscopic term) is the trap:
  it never flips and conserves everything to the last bit
- physics/3d/Force3d: the 2D forces with a Vec3 (uniform, gravitation,
  spring, drag, sum), and Archimedes, which is new: a body settles with
  exactly its relative density under the surface (0.6 for wood), the
  push at its centre for now, so nothing rights itself yet
- physics/3d/Hitbox3d, Contact3d, Collide3d: what a body *is* to a
  collision (sphere, turned box, capsule, plane, with their volumes and
  inertia tensors) and whether two of them overlap -- the closest
  points (segment/segment, box, triangle), every pair, and the rays
  (sphere, box, capsule, Moller-Trumbore for a triangle) that picking,
  aiming and a ground check are made of. The lesson is the box/box
  case: two boxes at an angle need their 6 face normals *and* the 9
  crosses of an edge of each, and Collide3d.boxes takes ~edge_axes:false
  so the classic bug can be watched. Its test went looking for a pair
  the 6-axis version gets wrong (20,000 random rods, 3 found) and keeps
  the first with a certificate computed straight off the corners.
  Not there, and said in the .mli rather than stubbed: GJK/EPA, convex
  hulls (which need their faces), triangle meshes, and contact
  manifolds (phase 8)
- physics/3d/Resolve3d: what happens after two hitboxes touch -- the
  impulse, with the inertia tensor inside its denominator
  (n . ((I^-1 (r x n)) x r) where 2D had (r x n)^2 / I), friction along
  two tangents (the pyramid every engine ships, 41% too strong on the
  diagonals, with the picture in the .mli), and the positional
  correction. The 2D engine's worked examples come out identical, which
  is the point: a ball into the end of a rod still gives it 0.4 of the
  speed and 1.2 rad/s. Momentum and angular momentum are conserved by
  construction and measured so over a thousand random collisions;
  energy is never created, and never lost with e = 1
- playground3d/Physics3d: bounce, bounce_off and bounce_all over it
- physics/3d/Solver3d and Collide3d.manifold: stacking. A contact
  manifold is a whole face, found by clipping the incident face against
  the reference face's four sides, so a crate resting on a crate
  touches at four corners and not one; and every contact of a step is
  then solved together, again and again (sequential impulses, warm
  starting, Baumgarte, a bounce threshold), which is what lets things
  be stacked rather than merely bounced. Measured, a crate dropped on
  the floor: solved, it rests 5 mm in and stops dead and goes to sleep;
  answered one pair at a time, it shivers at 5 cm/s for ever
- playground3d/Physics3d.world and simulate, with sleeping by islands:
  bodies that touch sleep as a group, because a crate sent to sleep
  alone under a tower that is still settling is woken a moment later
  with a jolt (measured: every 61 steps, the threshold plus one). A
  tower of five settles within 2 cm, creeps 3 mm sideways, and then
  costs nothing
- examples3d/PhysicsStack3d: a brick wall and a row of dominoes, "s" to
  turn the solver off and watch the wall come apart, "i" for the
  iterations, "w" for warm starting, space to throw a ball through it,
  and a marker over every body still awake -- they go out one by one,
  and at seven seconds the scene solves no contacts at all
- physics/3d rolling: the engine arrives at 5/7 g sin a on its own --
  1.805 m/s^2 measured on a 15 degree slope against the textbook's
  1.812, 3.488 on 30 degrees against 3.500, with v = w r at the contact
  to 2% -- having been told only about a tensor, a contact point and a
  friction impulse. games3d/TinyMarbleMadness derives that same 5/7 by
  hand in its header, so the two halves of the repository now check
  each other. With no friction the same sphere slides at exactly
  g sin a with no spin. Physics3d.spin_slow adds rolling friction,
  which is the other kind: rough is the grip that makes a ball roll,
  spin_slow the loss that stops it
- examples3d/PhysicsRoll3d: a race down a ramp between a frictionless
  ball (which wins), a solid sphere and a capsule lying across the
  slope, each labelled with the acceleration its own tensor predicts
  (a = g sin a / (1 + I/m r^2)) and the one the run measured: 3.03
  against 3.03, 2.16 against 2.16, 2.06 against 2.05
- physics/3d/Broadphase3d: which pairs are worth testing exactly -- all
  pairs, a hashed uniform grid, sweep and prune -- and what the third
  dimension changes about them. A dense 3D grid at 100 a side is a
  million cells, so the cells are hashed and only the occupied ones
  exist; and the sweep has to *choose* an axis, where 2D just took x:
  on a pile wide in x and z and thin in y, sweeping y costs 84,750 box
  tests against 6,644 for x, so the axis is picked by the variance of
  the centres. Measured on 500 marbles: 124,750 box tests for all
  pairs (0.75 ms), 1,340 for the grid (0.76), 7,472 for sweep and
  prune (0.22), all three finding the same 174 pairs
- examples3d/PhysicsMarbles3d: 200 marbles in a wireframe cage, space
  switching the method and the count of compared boxes on screen --
  nothing else changes, which is the point -- and "g" drawing the
  cells the grid actually keeps
- examples3d/PhysicsBounce3d: five balls of different bounciness
  dropped together, each with a bar drawn at e^2 of its fall from its
  bounciness alone -- the simulation comes back and touches it, ~2%
  under, which is the discrete step's cost and is on screen. And a
  crate dropped on its corner, where the impulse lands far from the
  centre and most of what it gets is spin
- examples3d/PhysicsHitbox3d: four shapes wearing their hitboxes as
  green wireframes, one you push through them with the arrows, and the
  contact drawn as an arrow along the way out, as long as the overlap
  is deep; 1/2/3 change what the one you push *is* without changing
  what it looks like, and "r" casts a ray
- playground3d/Physics3d: the Evan-style API over physics/3d, the same
  verbs as the 2D playground/Physics (body, at, moving, heavy, fall,
  push, thrust, slow, attracted_by, step, draw, debug) in metres rather
  than pixels, plus what 3D adds: pointing/turning an orientation
  instead of an angle, floating, spin_by, and a tensor taken from every
  body's own bounding box so that a body wobbles like the solid it
  looks like (upright takes it away, for a player or a flipper).
  Collisions are not in it yet, and the .mli names the gap
- games3d/StarCollector3d: ported behind physics=engine, as Asteroid
  was in 2D: the arrows push a body against drag, balancing at the same
  4.8 m/s the hand-written version moved at, the cube tumbling about a
  tilted axis (a quaternion drawn through rotate3d, which is where that
  conversion gets measured on something that moves), and "d" for what
  the engine sees, and its pickups are exact (Physics3d.touching, the
  player's turning box against each star's sphere) where by hand they
  are a distance between two centres. The default path is unchanged,
  golden frames byte-identical
- examples3d/PhysicsFloat3d: five blocks of different densities dropped
  into water, each settling at its own waterline, each wearing a stripe
  painted at that density -- nothing lines the stripes up with the
  surface but Archimedes. The arrows raise and lower the water and
  everything rises with it
- examples3d/PhysicsSpin3d: a T-handle thrown spinning, with nothing
  acting on it, that turns itself over and over -- the
  intermediate-axis (tennis racket, Dzhanibekov) theorem, the one piece
  of rigid-body behaviour with no 2D version. The angular momentum
  drawn as an arrow that never moves and the angular velocity as one
  that wanders; keys for the three axes and for how the spin is
  stepped, and both drifts printed honestly (|L| exact, the energy not:
  the flip multiplies any error by e^(4.6 t))
- games3d/TinyBoomerangFu3d: Boomerang Fu (2020), four foods in one
  arena, one boomerang each, one hit kills. The whole game follows from
  the weapon leaving your hand: while it is away you have only the
  dash, and while you hold it the dash is a slash that kills at arm's
  length. Three rules do the rest -- the way out cuts everyone, the way
  back is its owner's catch, and it comes back to where the owner *is*,
  steering at a moving target every frame -- plus one for the fence: a
  throw turns on the one who threw it once it has got away and caromed
  off something. The camera is fixed, high and nearly isometric,
  because a party game on one screen cannot follow anybody, and
  everything off the ground drags a shadow, which is the only depth cue
  that angle allows. The computer's three players use the same intent a
  human sends (a direction, a throw, a dash) and differ in four
  numbers; their hesitation before throwing is what makes the game
  playable at all, and their [clear_way] keeps last frame's direction
  while it stays clear, without which one wedged between a pit and a
  pillar shivers in a two-frame loop for a whole round. tests/games
  checks the return leg finds a thrower who kept running, who a flight
  cuts, the slash, and that the computer keeps out of the pits
- games3d/: TinyBattlezone (vector 3D), TinyWolfenstein3d, TinyVirtuaRacing,

** ai/ (new, game AI for teaching)
- ai/Minimax: minimax and alpha-beta side by side, each counting the
  positions it visits, so the cuts can be seen (tic-tac-toe searched to
  the end: 549,946 positions, 18,297 with alpha-beta)
- examples/AiTictactoe: searched to the end, so the computer can't
  lose, and each of your moves says WIN, DRAW or LOSS
- games/AiOthello: Othello against the computer, thinking 4 moves
  ahead, with its evaluation table of what each square is worth, and
  "v" to see what it thinks of each of your moves
- ai/Pathfind: breadth-first, Dijkstra and A* as the same search with a
  different queue, each counting the cells it looks at (an open 13x9
  grid: 80, 80, 11)
- examples/AiPathfinding: the frontier drawn as it spreads, walls and
  mud to paint, the three counts side by side
- ai/tests/: the .mli's tree, random trees where alpha-beta must agree
  with minimax, tic-tac-toe; the pathfinding worked example, A*
  agreeing with Dijkstra on random grids

  OCaml 5.5.1 to CI

  .gitignore/.codemapignore instead

** docs
- add CLAUDE.md summarizing the build commands and the virtual_modules
  native/web architecture
- add a "Making animated sprites" odoc page (playground/making_sprites.mld,
  linked from index.mld): animated GIFs, frames/delays vs the 60Hz game
  loop, how to make your own sprites
- Makefile: make website no longer does 'rm -rf docs' (which deleted the
  hand-written index.html, screenshots/, toy-*-example/, claude_notes/);
  it replaces only the odoc-generated dirs and also publishes the fresh
  web examples/games (.bc.js + .html) to docs/examples/ and docs/games/

** playground native
- image loading: replace imagelib (whose GIF decoder has a clear-code
  off-by-one bug, crashing e.g. on the Mario jump sprites) with
  stb_image; move the loading code to its own Image_native.ml{,i}
- run_app: cap the render loop to ~60fps (it was free-running at
  several hundred fps with no vsync, making games like Mario run ~7x too
  fast since their update functions use a fixed per-tick dt that assumes
  the web backend's requestAnimationFrame ~60Hz pacing)
- run_app: drain the whole SDL event queue each frame and always
  additionally deliver a Tick, instead of consuming at most one SDL event
  per loop iteration; a burst of queued input events (e.g. OS key-repeat
  while holding an arrow key) used to starve Tick delivery, which is the
  only message game physics reacts to, visibly slowing the game down
  while a key was held
- render_image: scale the decoded surface to fill the requested (w,h)
  box instead of just positioning its origin there; Cairo's
  set_source_surface doesn't resize content, so an image whose native
  decoded size differs from the requested size (e.g. Mario's 35x35 GIF
  sprites via "image 70. 70. ...") was drawn at native size, off-center
  (too small, floating above the ground instead of standing on it)
- add Playground_platform.preload_image (native: just enqueues a url;
  no-op on web) so a game can warm its sprite cache up front, like a
  loading screen, instead of lazily hitting the network mid-game;
  examples/Mario.ml now preloads all 6 sprite variants at init. run_app
  shows its window with a "Loading..." message, *then* synchronously
  downloads the queued urls (Image_native.load_queued), so there's
  visible feedback instead of a silent multi-second hang before any
  window appears. Tried a Thread-based background-loading cache first
  (avoids blocking but the sprite then pops in ~1s into gameplay, and
  needs a Mutex + creating Cairo surfaces off the main thread);
  preloading known-upfront assets is simpler and is what games normally
  do anyway, so dropped the threading in favor of it (Image_native.ml/.mli
  back to a plain synchronous cache)
- animated GIFs (e.g. Mario's walk sprites, turtle.gif) are now animated
  like in browsers: stb_image only decodes the first frame, so
  Image_native now splits a GIF into single-frame GIFs itself, decodes
  them with stb_image, composes them (frame patches, disposal methods),
  and render_image picks the frame from the current time
  (Image_native.surface_of_url_at)
- run_app/preload_image: parse -v/-verbose/-debug/-quiet (via Arg, one
  shared parse_cli_and_setup_logging for every example/game) and
  install a Logs reporter -- without one, Logs.xxx calls anywhere in
  this codebase were silently dropped, which is why e.g. Image_native's
  "loading/loaded image ..." Logs.info calls (the fix for the
  otherwise-silent multi-second stall while Mario preloads its sprites)
  needed -v to actually show up
- run_app: handle Sdl.Event.quit (exit 0) -- SDL posts this both when
  the window's close button is clicked and, on Unix, when the process
  gets SIGINT/SIGTERM (SDL's own signal handler turns those into this
  event instead of the default terminate-the-process behavior); without
  handling it, neither the close button nor e.g. Ctrl-C/`kill` did
  anything, since the event was received but silently ignored

** playground web
- run_app: deliver Ticks on a fixed 60Hz timestep instead of one per
  requestAnimationFrame, which fires at the display refresh rate (120Hz
  on Mac ProMotion screens), making Mario run 2x too fast
- run_app: patch the <svg> in place via a tiny virtual DOM (V.patch)
  instead of rebuilding it every frame; freshly created <svg:image>
  elements decode asynchronously, so the Mario sprite sometimes
  disappeared (and animated GIFs restarted every frame)
- preload_image: actually preload (and keep) the images, so switching
  sprites doesn't flicker
- render_image: set height (was setting width twice)
- mouse coordinates: convert via the root <svg>'s getScreenCTM() instead
  of the bounding box of the event target, which was the shape under the
  pointer (e.g. the circle in Mouse.ml), making the circle flicker and
  jump to wrong places; also handles the svg letterboxing
- render_words: render an svg <text> (centered, like elm-playground)
  instead of the placeholder circle; add a Prop attribute kind to the
  tiny virtual DOM to set its textContent
- render_polygon: render an svg <polygon> instead of the placeholder
  circle (fixes the ship and rocks in games_js/Asteroid)
- render_shape: render Group as an svg <g> instead of failing with "Todo"
- add Misc (polygon + group) to examples_js/
- run_app: pass the wall-clock time (Date.now) in Ticks, like the native
  backend and Elm, instead of the requestAnimationFrame timestamp
  (time since page load); games computing [now -. last_tick] with
  last_tick = Unix.gettimeofday() got a delta of about -1.8e9 seconds,
  making Tetris freeze the tab (space = full drop looped 1.8 billion
  times) and Asteroid never start
- Playground.to_frac: use float arithmetic, the wall-clock time in
  milliseconds does not fit in js_of_ocaml's 32-bit ints
- add docs/claude_notes/web_headless.js to run a web app in node with a
  fake DOM (hangs, exceptions, DOM dumps), documented in
  notes_debugging_techniques.txt

** playground (both backends)
- words: use the same font on native and web (Playground.words_font_size
  = 10, the old native size the games' scale factors were tuned with,
  and words_font_family = "sans-serif"); the web used the browser
  default (16px serif), so text was 1.6x bigger there. Native now also
  centers text like the web (advance width, font ascent/descent)

** build infra (web)
- examples_js/ and games_js/: copy the .html files into _build/ next to
  the .bc.js, so e.g. _build/default/examples_js/ can be opened directly
  in a browser; make now runs 'dune build @default' to include them

* 0.1 (Q4 2020) (refined prototype, dual native/web architecture)

** architecture
- switch native rendering from OCaml's Graphics to SDL2 (via tsdl),
  motivated by Graphics's inability to detect multiple simultaneous keys
  or keyUp/keyDown events (tried ocamlsdl2 too, see old Test_tsdl.ml /
  Test_ocamlsdl2.ml)
- switch the web backend from ocaml-vdom to plain DOM manipulation
- write Playground.mli as the single public API shared by both backends,
  ported from the comments of Elm's own Playground.elm

** playground
- coordinate system centered at (0,0), shapes (circle, rectangle, ngon,
  polygon, words, image, groups), rotation, computer/mouse/keyboard/screen
  records, and the picture/animation/game entry points
- image loading via imagelib, with curl-based fetch for remote URLs

** games and examples
- examples: Smiley, Picture, Animation, Mouse, Keyboard, Words, Turtle,
  Mario
- games: Snake, Pong, Tetris, Asteroid

** build infra
- dune
