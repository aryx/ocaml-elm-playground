* 0.3 (Q4 2026) (3D playground, from-scratch software rasterizers, OpenGL/WebGL, physics, audio, games)
# unless mentioned otherwise, everything below was done by Claude Code
# (with direction from me)

** playground3d (new)
- new elm_playground_3d library (Playground3d.mli), same Model-View-Update
  API as the 2D one: shape3d (cube, box, sphere, textured_quad,
  textured_cube, group3d), camera, lighting, flat/Gouraud/Phong shading,
  a HUD overlay (Playground3d.hud), portable rendering hints
  (Playground3d.rendering: shading, culling, textures), and cached3d
  (like Elm's Html.lazy, lets GPU backends keep a mesh in GPU memory)
- four backends: software (from-scratch rasterizer on SDL), web (reuses
  the 2D SVG renderer with a painter's algorithm), OpenGL (tgls) and
  WebGL, the last two sharing Gpu_scene and graphics/gpu/Mesh_cache;
  Minecraft3d went from ~6.5s to ~1ms per frame on OpenGL with cached3d
- textures from local files or http(s) urls, preload_texture, a magenta
  placeholder when a texture fails to load
- examples3d/ (Cube3d, Cubes3d, TexturedCube3d, InteractiveCube3d,
  Spheres3d, FloatingCity3d, PaintersAlgorithmFail3d, Corridor3d,
  CachedGrid3d) and games3d/ (StarCollector3d, Minecraft3d, a port of
  tiny-minecraft), each also built for web/opengl/webgl via copy_files
- fixes: spheres missing their top cap (Newell's method for face
  normals, the pole made the cross product 0 then NaN), 1-pixel cracks
  along shared triangle edges, a GC-timing bug in tgls'
  glShaderSource binding (Gc.full_major before compiling shaders)

** graphics/ (new, from-scratch rendering algorithms for teaching)
- private libraries independent of the Playground, one idea per module
  with its .mli explaining it (ASCII diagrams, paper references):
  core/ (Framebuffer, Blit, Opti), 2d/ (Fill scanline polygons, Line
  Bresenham, Circle midpoint, Stroke, Magnifier, geometry/Vec2), 3d/
  (Project, Cull, Clip, Zbuffer, Interpolate, Shading, Texture,
  Triangle with top-left fill rule and incremental edges, Painter,
  Render, geometry/ Vec3, Mat4, Camera, Lighting), font/ (Hershey vector
  fonts), images/ (Image_decode, Texture_decode, Rgba, Download), gpu/
  (Mesh_cache)
- unit tests in graphics/tests/ checking the worked examples of the .mli

** playground (2D)
- new software backend (elm_playground_software): a from-scratch 2D
  rasterizer on SDL (filled polygons, lines, circles, images by inverse
  mapping with bilinear/nearest filtering, Hershey text, antialiasing)
- portable rendering hints Playground.rendering (antialiasing,
  smooth_images) for run_app, honored by the Cairo, software and web
  backends; Mario uses it for sharp pixel-art sprites
- native_common/ (Native_loop_2d) shared by the Cairo and software
  backends
- fix: stb_image with ~channels:4 truncated RGB images (read past the
  end by Cairo); now load with the file's channels and expand to RGBA

** debugging and testing
- runtime-toggleable debug keys in the software backends (wireframe,
  bounding boxes, transparency, pixel magnifier, z-buffer vs painter,
  backface culling, perspective-correct vs linear, antialiasing,
  filtering, optimizations on/off, mesh cache), "h" for a help panel,
  only enabled with -debug-keys
- native flags -uncapped, -fixed-time t, -keys k, -dump-frame n file
  for deterministic frames; -v/-debug now also work in 3D
- golden frame tests (tests/2d/, tests/3d/) in make test, every software
  example rendered offscreen and compared pixel by pixel;
  make approve-golden2d/3d
- scripts: xdrive.py (drive a running app's mouse/keys via XTEST),
  ref_frames_3d.sh, bench_playground.sh, screenshot_playground3d.sh,
  smoke_test_playground3d.sh

** playground layers (2D, on top of Playground)
- Camera2d (window/lock/lerp following, zoom, clamp, an angle and
  turn_toward), Tilemap (levels typed as strings), Sprite (pixel art
  from strings, animated), Scene2d (title/playing/over scenes, keys
  pressed), Physics (see below), Audio (see below)
- Playground.flags: a program's parameters, name=value natively,
  ?name=value on the web (Playground_platform.flags); a seed=n flag
  for the games' randomness
- relative mouse motion (mdx/mdy), run_app3d ?capture_mouse (FPS look)

** games (the Tiny* toys) and kits
- kits/: racing (Road, Car, Topdown), maze (Grid_move, Chase), lightcycles
  (TinyTron's rules without a view)
- games/: TinyMario (was Platformer; pixel-art hero, sounds and
  music), TinyInvaders, TinySokoban (undo), TinyPacman, TinyWolf (a
  raycaster), TinyOutRun (pseudo-3D), TinyWorms, TinySpacewar, TinyPong,
  TinyCameltry, TinySlingshot, TinySoldat, TinyBomberman, TinyTron,
  TinyMicroMachines, TinyXpilot (the ball game on a rope, 1 or 2
  players), TinyGalaga (Catmull-Rom paths, by arc length),
  TinyDonkeyKong (state machines, slanted girders), TinyLodeRunner
  (digging), TinyRick (traps as tiles, flip-screen rooms), TinyGradius
  (the power-up bar, a timeline of waves), TinyZelda (rooms sliding
  in, an inventory), TinyRogue (a generated dungeon, turns),
  TinyStreetFighter (frame data, blocking, the quarter circle),
  TinyFinalFight (the belt, combos), TinyBabaIsYou (the rules as words
  on the board), TinyKart (Mode 7, row by
  row), TinyDoom (Doom's renderer: a node builder, the BSP walked
  front to back, per-column clip arrays, no z-buffer); kits/shmup (Shots, Path), kits/platformer (Tile_move,
  Ladder), kits/brawler (Hitbox, Frame_data, Stickman), kits/puzzle (Push,
  Undo) and
  kits/sectors (Sectors: a Doom level as sectors, its lines found)
- games3d/: TinyBattlezone (vector 3D), TinyWolf3d, TinyVirtuaRacing,
  TinyTron3d, TinyMario64, TinyMarble (Marble Madness), TinyDoom3d
  (TinyDoom's level with a z-buffer, no BSP); Minecraft3d is a game (walk, jump, fly,
  remove and place blocks, the targeted block's outline);
  playground3d's Camera3d (the 3D Camera2d: behind, chase, cockpit,
  orbit, sky); the OpenGL HUD redraws only what changed
- Mario, TinyMario, Asteroid: physics=engine, the Physics layer instead
  of their hand-written "dumb engine"
- the games' headers say which components they use; keys printed at
  launch

** physics/ (new, a 2D physics engine for teaching)
- physics/2d/: Body, Integrate (explicit/semi-implicit Euler, Verlet,
  RK4), Energy, Force, Shape, Collide (SAT, manifolds, swept tests),
  Contact, Broadphase (all pairs, grid, sort and sweep), Resolve
  (impulses, friction, rotation), Solver (sequential impulses, warm
  starting), Springs, Particles (Jakobsen's ropes and ragdolls),
  Kepler and Planets (orbits in closed form, JPL's elements)
- playground/Physics.mli, Evan-style: body, fall, push, thrust,
  attracted_by, step, touching, bounce, upright, world/simulate,
  went_through, pulled_to
- examples/: Orbit, Bounce, Marbles, Boxes, Pyramid, Elastic (each
  phase switchable off: solver=off, rotation=off), SolarSystem, and
  examples3d/PhysicsSolarSystem3d
- physics/tests/: the .mli's worked examples and the laws
  (conservation, convergence orders, stability limits)

** audio/ (new, a software synthesizer for teaching)
- audio/: Signal, Oscillator, Noise (the NES's LFSR), Envelope (ADSR),
  Mix, Synth (sounds as values, Euterpea's together/after), Mixer,
  Music, Abc (ABC notation), Doremi (solfège), Midi (Standard MIDI
  Files, read and written), Spectrum (DFT and FFT), Wav
- playground/Audio.mli, Evan-style and stateful: tone, square, noise,
  note; lasting, fading, sliding, together, after; blip, jump, coin...;
  play, keep_playing, loop, loop_from (a file or a URL: .mid, .abc,
  solfège); abc, doremi, midi
- sound natively (SDL's audio queue) and on the web (Web Audio, our own
  samples); -dump-audio file writes a run's sound as a WAV
- examples/Theremin, examples/Piano; TinyMario's sounds and an
  original looping tune (music=file-or-URL for one's own)
- the "v" debug key: an oscilloscope and a spectrum over the frame
- audio/tests/: worked examples and golden WAVs compared sample by
  sample (make approve-golden-audio)

** testing
- -script: game keys held over frames, for golden frames of gameplay
- tests/games/: scenario tests of the games' rules, played without

- scripts/ organized in subfolders, with the tools used for the games

* 0.2 (Q3 2026) (bugfixes, Dockerfile, CI hardening, cleanup)
# started to use Claude code

** build infra
- add Dockerfile and configure script, plus a docker.yml GHA workflow
- drop the stale ocaml < 5.2.0 upper bound on elm_playground_native, add
  OCaml 5.5.1 to CI
- Makefile: fix make visual, use osemgrep from PATH
- delete skip_list.txt and the codemap/martin's-lib cruft, rely on
  .gitignore/.codemapignore instead

** docs
- add CLAUDE.md summarizing the build commands and the virtual_modules
  native/web architecture
- add a "Making animated sprites" odoc page (playground/making_sprites.mld,
  linked from index.mld): animated GIFs, frames/delays vs the 60Hz game
  loop, how to make your own sprites
- Makefile: make website no longer does 'rm -rf docs' (which deleted the
  hand-written index.html, screenshots/, toy-*-example/, claude_notes/);
  it replaces only the odoc-generated dirs and also publishes the fresh
  web examples/games (.bc.js + .html) to docs/examples/ and docs/games/

** playground native
- image loading: replace imagelib (whose GIF decoder has a clear-code
  off-by-one bug, crashing e.g. on the Mario jump sprites) with
  stb_image; move the loading code to its own Image_native.ml{,i}
- run_app: cap the render loop to ~60fps (it was free-running at
  several hundred fps with no vsync, making games like Mario run ~7x too
  fast since their update functions use a fixed per-tick dt that assumes
  the web backend's requestAnimationFrame ~60Hz pacing)
- run_app: drain the whole SDL event queue each frame and always
  additionally deliver a Tick, instead of consuming at most one SDL event
  per loop iteration; a burst of queued input events (e.g. OS key-repeat
  while holding an arrow key) used to starve Tick delivery, which is the
  only message game physics reacts to, visibly slowing the game down
  while a key was held
- render_image: scale the decoded surface to fill the requested (w,h)
  box instead of just positioning its origin there; Cairo's
  set_source_surface doesn't resize content, so an image whose native
  decoded size differs from the requested size (e.g. Mario's 35x35 GIF
  sprites via "image 70. 70. ...") was drawn at native size, off-center
  (too small, floating above the ground instead of standing on it)
- add Playground_platform.preload_image (native: just enqueues a url;
  no-op on web) so a game can warm its sprite cache up front, like a
  loading screen, instead of lazily hitting the network mid-game;
  examples/Mario.ml now preloads all 6 sprite variants at init. run_app
  shows its window with a "Loading..." message, *then* synchronously
  downloads the queued urls (Image_native.load_queued), so there's
  visible feedback instead of a silent multi-second hang before any
  window appears. Tried a Thread-based background-loading cache first
  (avoids blocking but the sprite then pops in ~1s into gameplay, and
  needs a Mutex + creating Cairo surfaces off the main thread);
  preloading known-upfront assets is simpler and is what games normally
  do anyway, so dropped the threading in favor of it (Image_native.ml/.mli
  back to a plain synchronous cache)
- animated GIFs (e.g. Mario's walk sprites, turtle.gif) are now animated
  like in browsers: stb_image only decodes the first frame, so
  Image_native now splits a GIF into single-frame GIFs itself, decodes
  them with stb_image, composes them (frame patches, disposal methods),
  and render_image picks the frame from the current time
  (Image_native.surface_of_url_at)
- run_app/preload_image: parse -v/-verbose/-debug/-quiet (via Arg, one
  shared parse_cli_and_setup_logging for every example/game) and
  install a Logs reporter -- without one, Logs.xxx calls anywhere in
  this codebase were silently dropped, which is why e.g. Image_native's
  "loading/loaded image ..." Logs.info calls (the fix for the
  otherwise-silent multi-second stall while Mario preloads its sprites)
  needed -v to actually show up
- run_app: handle Sdl.Event.quit (exit 0) -- SDL posts this both when
  the window's close button is clicked and, on Unix, when the process
  gets SIGINT/SIGTERM (SDL's own signal handler turns those into this
  event instead of the default terminate-the-process behavior); without
  handling it, neither the close button nor e.g. Ctrl-C/`kill` did
  anything, since the event was received but silently ignored

** playground web
- run_app: deliver Ticks on a fixed 60Hz timestep instead of one per
  requestAnimationFrame, which fires at the display refresh rate (120Hz
  on Mac ProMotion screens), making Mario run 2x too fast
- run_app: patch the <svg> in place via a tiny virtual DOM (V.patch)
  instead of rebuilding it every frame; freshly created <svg:image>
  elements decode asynchronously, so the Mario sprite sometimes
  disappeared (and animated GIFs restarted every frame)
- preload_image: actually preload (and keep) the images, so switching
  sprites doesn't flicker
- render_image: set height (was setting width twice)
- mouse coordinates: convert via the root <svg>'s getScreenCTM() instead
  of the bounding box of the event target, which was the shape under the
  pointer (e.g. the circle in Mouse.ml), making the circle flicker and
  jump to wrong places; also handles the svg letterboxing
- render_words: render an svg <text> (centered, like elm-playground)
  instead of the placeholder circle; add a Prop attribute kind to the
  tiny virtual DOM to set its textContent
- render_polygon: render an svg <polygon> instead of the placeholder
  circle (fixes the ship and rocks in games_js/Asteroid)
- render_shape: render Group as an svg <g> instead of failing with "Todo"
- add Misc (polygon + group) to examples_js/
- run_app: pass the wall-clock time (Date.now) in Ticks, like the native
  backend and Elm, instead of the requestAnimationFrame timestamp
  (time since page load); games computing [now -. last_tick] with
  last_tick = Unix.gettimeofday() got a delta of about -1.8e9 seconds,
  making Tetris freeze the tab (space = full drop looped 1.8 billion
  times) and Asteroid never start
- Playground.to_frac: use float arithmetic, the wall-clock time in
  milliseconds does not fit in js_of_ocaml's 32-bit ints
- add docs/claude_notes/web_headless.js to run a web app in node with a
  fake DOM (hangs, exceptions, DOM dumps), documented in
  notes_debugging_techniques.txt

** playground (both backends)
- words: use the same font on native and web (Playground.words_font_size
  = 10, the old native size the games' scale factors were tuned with,
  and words_font_family = "sans-serif"); the web used the browser
  default (16px serif), so text was 1.6x bigger there. Native now also
  centers text like the web (advance width, font ascent/descent)

** build infra (web)
- examples_js/ and games_js/: copy the .html files into _build/ next to
  the .bc.js, so e.g. _build/default/examples_js/ can be opened directly
  in a browser; make now runs 'dune build @default' to include them

* 0.1 (Q4 2020) (refined prototype, dual native/web architecture)

** architecture
- switch native rendering from OCaml's Graphics to SDL2 (via tsdl),
  motivated by Graphics's inability to detect multiple simultaneous keys
  or keyUp/keyDown events (tried ocamlsdl2 too, see old Test_tsdl.ml /
  Test_ocamlsdl2.ml)
- switch the web backend from ocaml-vdom to plain DOM manipulation
- write Playground.mli as the single public API shared by both backends,
  ported from the comments of Elm's own Playground.elm

** playground
- coordinate system centered at (0,0), shapes (circle, rectangle, ngon,
  polygon, words, image, groups), rotation, computer/mouse/keyboard/screen
  records, and the picture/animation/game entry points
- image loading via imagelib, with curl-based fetch for remote URLs

** games and examples
- examples: Smiley, Picture, Animation, Mouse, Keyboard, Words, Turtle,
  Mario
- games: Snake, Pong, Tetris, Asteroid

** build infra
- dune

* Beta (2020-11-26) (few basic games)

- initial native (via TSDL) and web (via vdom) backends, and a few basic
  games (Pong, Asteroid, Snake, and even Tetris!) working in native and a
  few working in web

* Alpha (2020-11-02) (first proto)

- start from a single lib/ (SVG-based) prototype, then a separate lib2/
  using Graphics, before settling on the current split: core/ (Basics,
  Color, Set_, Keyboard, Time) <- system/ (Cmd, Sub) <- playground/, with
  playground/Playground_platform.mli as a dune virtual_modules interface
  implemented separately by playground/native/ (tsdl/SDL2 + cairo2) and
  playground/web/ (js_of_ocaml)

- first commits and first prototype, during a "procrastination week" while at R2C
  (now Semgrep) post-launch when I fell in love with Elm, its creator Evan,
  and later Evan's gem that is the elm playground (video games making nostalgia!
  part of the reason I started computer programming). I even did a weekly-demo
  about it at R2C :)
