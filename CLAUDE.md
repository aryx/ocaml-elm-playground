# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ocaml-elm-playground` is an OCaml port of Evan Czaplicki's [elm-playground](https://github.com/evancz/elm-playground): a library for making pictures, animations, and simple video games (using the Elm "Model-View-Update" architecture) that run either natively (SDL/Cairo desktop app) or in the browser (js_of_ocaml + vdom), from the *same* application code.

## Build, test, and doc commands

```bash
make               # = dune build (also regenerates the *.opam files)
make test           # = dune runtest -f
make clean          # = dune clean
dune build @doc     # build odoc API docs (make doc does this too)
dune build games/fps/web --profile=release-js # build a genre's web games with small .js output (make js: all)
dune build examples/web --profile=release-js  # same, for examples
```

Run a single native example/game directly with dune, e.g.:
```bash
dune exec examples/Keyboard.exe
dune exec games/arcade/Snake.exe
```

Web (`js/`) targets are executables built in `(modes js)`; after building, the resulting `.bc.js` is copied next to the corresponding `.html` file in `examples/web/`/`games/<genre>/web/` (see the `website`/`js` Makefile targets and the README's "Simple web application" section for the manual `dune build --root . && cp _build/default/Toy.bc.js static/` pattern used by the two toy example projects under `docs/`).

`make test` also runs the golden frame tests (`tests/2d/`, `tests/3d/`,
see `tests/common/Testutil_golden.mli`): every software-rasterizer
example rendered offscreen (SDL's dummy video driver) and compared pixel
by pixel with `tests/*/golden/*.png`. The scenes are data,
`tests/common/scenes/Scenes_2d.ml` and `Scenes_3d.ml` (a new game adds
its own there), which tinybox's menu reads too. After an intended pixel change,
look at the new frames in `_build/default/tests/*/actual/`, then
`make approve-golden2d` / `make approve-golden3d`.

`make test` skips the scenes deep into a game (more than 100 frames to
render: each is seconds of CPU, and they run in parallel), keeping every
example's frames and the first frame of each game. `make
test-golden-all` runs those too -- before a release, or after touching a
renderer.

The native software backends' debug keys (rendering toggles, "h" for
help) only work when run with `-debug-keys` (e.g.
`dune exec examples/Cubes3d.exe -- -debug-keys`), and with Ctrl held:
the platform's keys are all Ctrl + a key (Ctrl+Q quits), a plain key
is always the program's. What a program that is not a game changes of
its window is one record, `run_app ~window:{ Playground.default_window
with ... }` (`Playground.window`: a new such option is a field of it,
not an argument of `run_app`): `platform_keys = false` gives the
program every key; `skip_same_view = true` (an application's,
mini-chrome's) does not draw a frame whose view is the list (`==`) of
the frame before, unless an event came (`-uncapped` and `-debug-keys`
draw every frame anyway); `screen_size` and `follows_window` are below.
Other flags:
`-uncapped`, `-fixed-time t`, `-keys k`, `-dump-frame n file`,
`-script "right:1-60,space:30"` (game keys held over frames). The
native Cairo and OpenGL windows can change size (dragged, `-size WxH`,
`-fullscreen`, Alt+Enter toggling full screen): the program's screen
stays 1000 by 1000 -- or the shape a program asks for, the window's
`screen_size = Some (w, h)`, told to it by a first `Resized` (`Sub.on_resize`,
which `game` follows), native Cairo only (tinybox's menu: 1778 by
1000, 16:9) -- drawn scaled to fit, centred, black bars round it
(`Native_loop_2d.scale`); the software platforms' windows stay 1000 by
1000, the golden frames' size.

`make check` runs the project's semgrep config (`semgrep.jsonnet`) via a local `osemgrep` binary — not generally runnable outside the author's machine.

## Architecture

### Virtual module split: one API, two backends

The whole library hinges on dune's `virtual_modules` mechanism:

- `playground/Playground.mli` + `playground/Playground.ml` (library `elm_playground`) define the **entire public API**: shapes, colors, `computer`/`mouse`/`keyboard`/`screen` records, animation helpers (`spin`/`wave`/`zigzag`), and the three entry points `picture`, `animation`, `game` which all produce a `('model, 'msg) app` value.
- `playground/Playground_platform.mli` declares a single virtual function, `run_app : ('a, 'b) Playground.app -> unit`. The `elm_playground` library declares this as a `virtual_modules Playground_platform` in `playground/dune` — it has no implementation.
- Two separate libraries each provide a concrete `Playground_platform.ml` and `(implements elm_playground)` in their dune file (the backends all sit in `playground/platforms/`):
  - `playground/platforms/native/Playground_platform.ml` → library `elm_playground_native` (SDL2 via `tsdl`, 2D drawing via `cairo2`, images decoded by our own `graphics/images/`, HTTP and HTTPS by our own `networking/` -- TLS 1.3 from scratch, `plan_tls.md` -- logging via `logs`).
  - `playground/platforms/web/Playground_platform.ml` → library `elm_playground_web` (DOM/vdom via the `vdom` library, compiled with js_of_ocaml).
- The 3D playground is the same split, in the same directories: `playground/Playground3d.mli` (library `elm_playground_3d`, virtual module `Playground3d_platform`), implemented by `playground/platforms/native/Playground3d_platform.ml` (`elm_playground_3d_opengl`), `playground/platforms/software/` (`elm_playground_3d_software`), `playground/platforms/web/` (`elm_playground_3d_webgl`) and `playground/platforms/svg/` (`elm_playground_3d_web`, the scene compiled to 2D shapes drawn as SVG). A directory holds a 2D and a 3D library side by side, each stanza listing its `(modules ...)`: the libraries (and opam packages) stay separate, so a 2D program needs no OpenGL. The SVG backend has its own directory because its implementation module has the same name as WebGL's.
- The rest of `playground/` is in folders, not libraries (`(include_subdirs unqualified)`, `playground/README.md`): `apis/` (the Evan-style APIs over the from-scratch libraries: `Audio`, `Physics`, `Ai`, `Gui`, `Juice`, `Multiplayer`, their `*3d` and `*_debug` twins), `layers/` (`Camera2d`, `Sprite`, `Tilemap`, `Scene2d`, `Camera3d`, `Character3d`, `Ragdoll3d`, `Portal3d`), `ways/` (`Logo`, `Logo3d`, `Bigbang`, `Universe`, `Puzzlescript`, `Karel`, `Povray`, POV-Ray's way: a scene of solids, CSG, lights, mirrors and glass, ray traced progressively, each of the ray tracer's algorithms kept and shown side by side with the flag `evolution`). Their modules belong to `elm_playground` or `elm_playground_3d` wherever they sit (the 3D stanza lists its modules by name); the backends' folders (under `platforms/`) and `tests/`, which have stanzas of their own, say `(include_subdirs no)`.

Every example/game module (`open Playground; ... let main = Playground_platform.run_app app`) is therefore **backend-agnostic source code**. The `examples/`, `games/<genre>/` dune files link against `elm_playground_native`; the `examples/web/`, `games/<genre>/web/` subdirectories reuse the exact same `.ml` files via `copy_files` (a build-time copy, not a committed symlink or duplicate -- there is only one real source file per example/game) and link the result against `elm_playground_web` with `(modes js)`. The 3D examples (`*3d.ml`) sit in `examples/` too, with a second `executables` stanza per dune file (each stanza listing its `(modules ...)`): OpenGL (`elm_playground_3d_opengl`) at the top level, `elm_playground_3d_software` in `examples/software/`, WebGL (`elm_playground_3d_webgl`) in `examples/web/`, and SVG (`elm_playground_3d_web`) in `examples/svg/`, which has only 3D examples. A genre's 3D games (`games/<genre>/`) are laid out the same way, WebGL in its `web/`. `examples/dune`'s OpenGL stanza (unlike the games') is missing five 3D examples that `examples/software/` has (`Cube3d`, `InteractiveCube3d`, `PaintersAlgorithmFail3d`, `FloatingCity3d`, `Corridor3d`) -- see `examples/dune`'s trailing comment for why.

### Supporting libraries

- `libs/` → the from-scratch libraries, independent of the Playground (`libs/README.md`): `core/`, `random/`, `crypto/`, `compression/`, `graphics/`, `physics/`, `audio/`, `ai/`, `networking/`, `gui/`, `juice/`, `terminal/` (the VT100's screen, `Vt`, the tty's `Line_discipline`, `Talk`, the programs that ask and wait as values and the machine playing one, `Curses` and `Tui`, the full-screen programs, and `unix/`'s `Tty_unix`, which runs one in a real terminal, native only: `plan_terminal.md`). The rule: a module there knows pixels, samples, bodies, bytes or rectangles, never shapes and `computer`s; the Playground's `apis/` is where games meet them. dune finds them by name, so moving one never changes a dependent's dune file. They are the opam package `tiny_libs`, below `elm_playground`, which depends on it: each library public as `tiny_libs.<its name>` (a new one needs `(public_name tiny_libs.<name>)`, and its modules in `libs/index.mld`, the package's odoc front page), so that a program outside the repository can use them; inside, the short name. The bullets below name them by their folder under `libs/`.
- `languages/` → languages as text, parsed and run, no Playground, at the top beside `appkits/` and `gamekits/` (not in `libs/`: each is made for a program or a few, so it is their code and counts toward their budget, `languages/README.md`): `formula/`, the spreadsheet's `Formula`; `basic/`, BASIC over `Talk`; `sexpr/`, the reader the Lisps share (`Sexpr`, a tree with spans; `Sexpr_read`, Emacs's dialect and Scheme's); `lisp/`, a small Emacs Lisp, dynamically scoped, its state a value threaded through eval, for TinyEmacs; `scheme/`, a small Scheme and HtDP's Beginning Student, run by a CESK machine (call/cc, tail calls, fuel), its images as data, and the stepper (`Scheme_step`), for TinyDrScheme; `pascal/`, Pascal compiled in one pass to P-code (`Pascal_compile`, `Pcode`) and run by the P-machine (`Pmachine`, a Talk program, or paused), with its debugger (`Pdebug`) and a disk of classics (`Pascal_disk`), for TinyTurboPascal; `hypertalk/`, HyperCard's language, a world of fields and cards given as functions, for TinyHyperCard and TinyMyst; `smalltalk/`, Smalltalk-80 from the Blue Book, compiled to its bytecodes and run by its interpreter over an object table, its kernel classes in Smalltalk (`kernel/*.st`) bootstrapped by `St_boot`, for TinySmalltalk80 (`plan_tiny_smalltalk.md`, `notes_smalltalk.md`), and a second kernel, Squeak's (`St_kernel.squeak`: the Blue Book's files then `kernel/squeak/*.st`, never the reverse; its `BlockClosure` class is what makes the compiler emit closures), for TinySqueak to come (`plan_tiny_squeak.md`, `notes_squeak.md`); `scratch/`, Scratch's blocks and Snap!'s as one table of specs (`Scratch_blocks`), their scratchblocks text read and printed (`Scratch_text`), a project run, each script a green thread yielding at the end of a loop's turn, Snap!'s heap, environments and closures (`Scratch_run`), for TinyScratch and TinySnap. JavaScript is `javascript/`, TinyFirefox's (`plan_tiny_firefox.md`); `ocaml/` is tinybox's code map's, over `libs/code/highlight` (`Highlight_code`, the categories and colours any language's highlighter gives). `html/` and `css/` are the browsers', laid out by `appkits/browser/layout`. They are the opam package `tiny_languages`, on `tiny_libs`: each library public as `tiny_languages.<its name>` (a new one needs `(public_name tiny_languages.<name>)`, may use only `tiny_libs`' libraries and other languages, and its modules go in `languages/index.mld`, the package's odoc front page).

### The Model-View-Update pattern

`game view update initial_state` (see `playground/Playground.ml` and the README example) builds an `app` from:
- a `view : computer -> 'model -> shape list` function,
- an `update : computer -> 'model -> 'model` function,
- an initial model value.

`picture` and `animation` are simplified special cases of the same `app` type (`picture : shape list -> (screen, msg1) app`, `animation : (time -> shape list) -> (animation, msg) app`). The playground coordinate system is centered at `(0, 0)` (not top-left), which is a deliberate deviation from typical screen coordinates — keep this in mind when writing or debugging view code.

### The catalogue

`CATALOG.md` lists every game (`games/<genre>/`, a section per genre) and app (`apps/`), one table row each: name linked to its source, how it is drawn (2D, 2.5D, 3D), the original it is after, a one-line description (a future tooltip). A new game or app gets its row there; the screenshot and web page are found by convention (see the file's introduction). `tests/catalog/` checks it in `make test`: every executable named in the genres' and `apps/`'s dune files needs its row, its golden frame (`tests/2d/golden/<Name>.png`, `tests/3d/` for a 3D game) and its web page (`<dir>/web/<Name>.html`), and every row must name an existing program. It also checks the budget: a program's own code -- its file and the modules of its folder, of the kits (`gamekits/`, `appkits/`) and of the languages (`languages/`) it names, as tinybox's code map counts it (`launcher/codemap/deps/Code_deps`) -- is at most 5,000 lines, `libs/` and `playground/` not counted (general, not a program's; README's "A budget"); six exceptions, each carrying a whole language, are listed in `tests/catalog/Unit_catalog.ml`'s `over_budget`, and the test fails when one comes back under.

### tinybox, every program in one binary

`launcher/` builds `tinybox` (opam package `tinybox`, installed by `make install`; after a `make`, also `./bin/tinybox`, `bin` being a committed symlink to `_build/install/default/bin` that the root `dune` keeps dune out of), after BusyBox: every game and app linked into one executable, `tinybox list`, `tinybox mario [args]`, `tinybox TinyVi -tty` (`docs/claude_notes/plans/plan_launcher.md`). `tinybox` alone opens its menu (`launcher/menu/Tinybox_menu.ml`, a 2D Playground game after Batocera's and RetroBox's front ends, the same natively and in a browser over a host record: `launcher/native/` is tinybox itself and `Tinybox_native`, the programs linked in, one started as a child process, the previews; `launcher/web/` is `Tinybox_web`, 0.4 MB, no program linked in, one started by loading its own page, published as `docs/tinybox.html` by `make website`; `plan_tinybox_web.md`), which shows `CATALOG.md` (read by `launcher/catalogue/`) with each program's first golden frame as its screenshot, both embedded at build time by the generator in `launcher/codegen/` -- so a new row or an approved golden frame changes the menu, and the thumbnails are rebuilt (8 shards, ~8 s). It works because every program's main is `let main = Program.main __MODULE__ (fun () -> ...)` (`libs/core/Program.mli`, enforced by semgrep's `main-through-program`): run at once in the program's own .exe, only recorded inside tinybox, which runs the one chosen with its own command line (`Program.argv`). `s` in the menu opens the chosen program's code map (`launcher/codemap/`, after the author's codemap: its own code -- its file and the kits' modules it uses, each in its folder -- then, `w`, with all it uses, then the whole repository, as a squarified treemap under a camera -- the wheel zooms at the mouse, a click flies in, the code readable on the map up close, definitions written large from afar -- the code drawn in the VGA's 8 by 16 font, `Vga_font`, a file read in `Code_view`; the files numbered in reading order, and `n` a tour of their headers, sections and "the trick of this game" marks, each read in `Code_view`), over every source of the repository embedded at build time (`Tinybox_sources`, 10 MB) and coloured by `languages/ocaml`'s `Highlight_ml` (`plan_tinybox_codemap.md`). So a program must do nothing at its top level that belongs in its main: no reading the command line (`Playground_platform.flags ()` only inside `main`), nothing slow (make big tables `lazy`); `make test` runs `tinybox list` to catch both. A new program's library must also be added to `launcher/native/dune`'s list (the link fails until it is), and a new genre or app folder gets its `copy_files` line there. 2D is Cairo's, 3D OpenGL's: the OpenGL backend compiles its own copy of the HUD rasterizer (`Hud_render`) so as not to depend on the software 2D platform (see `playground/platforms/native/dune`).

### opam packages are generated, not hand-edited

`dune-project` has `(generate_opam_files true)` and declares a `(package ...)` stanza per public library (`tiny_libs`, the libraries of `libs/`, each `tiny_libs.<name>`, `elm_core` as `tiny_libs.core`; `tiny_languages`, those of `languages/`, on it; `tiny_appkits`, those of `appkits/`, on both; `elm_playground_gamekits`, those of `gamekits/`, above the Playground; `elm_playground`, which depends on it, `elm_playground_native`, `elm_playground_software`, `elm_playground_web`, `elm_playground_3d`, `elm_playground_3d_opengl`, ..., `tinybox`) with their dependencies; all are released together, one version, from one archive of the tag that every package downloads; `.gitattributes` keeps `docs/` out of it (`export-ignore`, why and how to check in the file). Each package builds and tests alone (`dune build -p <pkg> @runtest`, as opam's CI does): every test stanza and `runtest` rule has the `(package ...)` it tests, and the golden frames are skipped in release builds (the root `dune`'s `GOLDEN=none`). The libraries shared by the native backends (`playground/platforms/native_common/`) are private, installed as part of `elm_playground_software` (see `playground/platforms/native_common/dune` for why, and the caveat). The `*.opam` files at the repo root are generated from this — edit `dune-project`, then run `make` (or `dune build <name>.opam`) to regenerate them, rather than editing the `.opam` files directly. `elm_playground_native.opam.template` is the one exception (hand-maintained template consumed during opam generation for that package).

### Docs (`docs/`)

`docs/` is the published GitHub Pages site (served from the `master` branch's `/docs` folder per repo settings) — it is *generated* output (`make website`: `dune build @doc` then copy `_build/default/_doc/_html` to `docs/`, plus `make js` to build the release-mode JS bundles for `examples/web`/`games/<genre>/web`). The API docs' front page is `playground/index.mld`: after the tutorial, "The library, area by area", a section per area (anchors `#playground`, `#graphics`, ..., `#gamekits`, `#languages`, linked from the README's area table and `docs/index.html`) listing its modules by hand, those of other packages (`elm_playground_3d`, `elm_playground_software`, `elm_playground_3d_software`) as relative links -- a new library module gets its line there. `docs/toy-native-example/` and `docs/toy-web-example/` are the two minimal standalone example projects referenced in the README's "Simple native/web application" walkthroughs; keep them in sync with the corresponding README code snippet (see the `coupling:` comment in `README.md` referencing `docs/toy-native-example/toy.ml` and `examples/Keyboard.ml`).
